S5. “Diagnosticar antes de construir.” Trace one delivery, not an entire application. The project can be new or already underway; an existing delivery is the cheapest source of evidence, not a product dependency. Follow the intent or base document, the question and selection, the work, its checks, the artifact or integration, and the result visible to the operator. Cite an existing reference for each observed step; mark missing steps unknown. Distinguish OpenCode's conversation, ODD's decisions, Gas Town's execution, Nix's declaration and the local Go commands. Identify an observed benefit, duplication or gap; do not assume another wrapper is needed.

The operator should be able to ask “ver como va como estan los entregables.” with just the project name and get an answer: what was delivered, what proves it, what remains unknown, and which functional or architectural decision, if any, is theirs. Start with the answer the operator actually received, if recorded. Distinguish a Gas Town report from an answer OpenCode assembled on request. Either can serve the operator without requiring them to find a branch or run a command. Evidence found only during a later inspection can corroborate delivery; it cannot prove either channel showed it.

If the ordinary interaction already answers the question accurately, recommend no change to that workflow. Otherwise identify the first evidenced gap, or say what evidence is missing. A status answer about an existing delivery does not prove that a new project can start from its base documentation, that the application works, or that voice works. The later goal (“el dia de mañan tiene que ser por voz”) remains the same conversation on a simpler channel.
