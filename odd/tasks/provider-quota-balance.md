# provider-quota-balance

Objective: route OpenCode roles and Gas Town chains across anthropic, openai and ollama-cloud so each provider's quota depletes in step with its billing window and none runs out mid-month, without manual profile switching.
Branch: `feat/model`. Delivery strategy: `ask-on-risk`, forecast about 250 authored lines, work-unit commits on the branch; push, PR and activation left to the user. Scope: rog only (L35). Test runner: `nix fmt -- <paths>`, `nix flake check --no-build`, host `nix eval` of affected Home Manager targets.

## Specs

S1. "la idea es tener una lista que vea costo rendimiento pero que los limites en general me ayuden a alcanzar a fin de mes incluso con gastwon" — the routing accounts for Gas Town consumption, not only interactive OpenCode.
S2. "no quiero estar cambviando a eopnai-ahtropic y luego a anthropic-medium y asi es teiosos" — no manual profile switching is needed during the month.
S3. (Deprioritized by user 2026-11-18, L17: "igual me da igual si temrinan al mismo tiempo.") "con los 3 provedores que tengo anthropic openai y ollama podmaso genrar un balance para que se consuman a mismo tiempo los limnites vayan llegando pero no quedar a medio caminio porque uno se conumio mas que el otro" — acceptance: per provider, percent of quota used tracks percent of its window elapsed; no provider exhausts while others keep large unused headroom.
S4. "i ula podemos usar el patron acutal como backups o fallabcks" — existing profiles may serve as fallback chains instead of one single list. Candidate mechanism (assumption, not yet verified on OpenCode 2.2.7): `@azumag/opencode-rate-limit-fallback` v2 (`plugins` key, ordered `fallbackModels`, 429/quota detection, subagent support).
S5. "partamos con provider base nix" — the first delivery changes `shared/opencode/providers-base.nix`.
S6. "yo veo : opus o astra como big orqeusador o nivel genral. sol y sonnet luego. pero aveces igual hay que vovler al high tier porque sonnet y sol se desvian" (supersedes the earlier "sonnet como orquesador") — two orchestrator tiers: a big tier (`claude-opus-5-5` / `gpt-6-astra`) shapes the macro plan "hasta que lo macro este maduro", then a mid tier (`claude-sonnet-5-5` / `gpt-6.1-sol`, and models "a la altura de sonnet" such as `glm-5.3`) executes it; work returns to the big tier when the mid tier drifts. Worker: "luego worker lo mas barato y efectivo", passing model-fit Gates 1-2.
S8. "la idea es que solo high tier este como orquestodr. too lo demas de sonent sol para abajo." — big-tier models (`claude-opus-5-5`, `gpt-6-astra`) are assigned only to `gentle-orchestrator`; every subagent role (explore, worker, verify, review, jd) uses mid tier (`claude-sonnet-5-5`, `gpt-6.1-sol`) or below.
S7. "a menos que la base de opsu y astra hace que sonnet y sol no se desbien" — hypothesis to test: a big-tier feature document (verbatim specs, tasks, routes) keeps the mid tier from drifting. Evidence found: OpenCode V2 stores the session model separately from the agent ("Selecting a primary agent by ID does not change that model", https://opencode.ai/docs/agents), so a tier change is an in-session model switch with no profile rebuild.
