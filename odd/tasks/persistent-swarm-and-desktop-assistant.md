### L5 — Proposed two-plane architecture

**A: development swarm.** A coordinator owns task decomposition, status, checkpoints, and bounded specialist work. A persistent server hosts execution so closing a phone/laptop client does not intentionally terminate jobs. The proposed starting experiment uses Hermes native delegation and at most two workers, not an unrestricted swarm. This limit and the phone channel are proposals, not selected configuration.

The execution identity, HOME, workspace roots, model credentials, and state must be distinct from personal-desktop authority. Herdr may provide operator visibility and maintenance access; it is not a mandatory nesting layer around every daemon. A dedicated account or VM boundary must be selected after checking actual enforcement, resource cost, and whether container/build control would grant broader host access.

A distribution is a possible future workload, not the first autonomous assignment. Start with one small, disposable development task. Multi-day recovery, build queues, destructive operations, and publication need evidence before expanding to a distribution project. Repository data and tests, not chat claims, determine completion.

**B: personal-session assistant.** A separate executor receives only the chosen browser/desktop capability and approved task scope. Start by proving controls against synthetic data, then request explicit authorization for one named real session and workflow. A rehearsal profile is a safety test, not a substitute for the final personal-session objective.

Do not give A the B tool registry, browser profile, desktop sockets, input devices, or a command bridge to B. Sharing a model provider does not require sharing credentials, tool authority, or memory. A separate OS username alone ceases to be an effective desktop boundary if it is then granted broad access to the personal display/input/session bus.

**Ownership and exit.** The operator owns host administration, channel/account pairing, provider billing, and deployment decisions. Candidate services add updates, state backups, and resource monitoring. Before stopping a trial, preserve/export its outputs and relevant state; stop only the trial's processes and revoke its grants. Do not delete users, volumes, worktrees, or browser profiles as an automatic rollback.

### L7 — Proposed experiments and acceptance evidence

These are test designs, not executed tests or newly authorized actions. Future behavior changes need deterministic RED/GREEN coverage where meaningful, plus an independent verifier for security-sensitive implementation. Use disposable state; preserve the pre-change baseline and test rejected commands for unchanged data and existing behavior.

**Experiment A — Can a bounded development task be delegated and controlled from a phone without losing continuity or exhausting the host?**

1. Select a small disposable repository task with a deterministic expected result; record baseline data and resource state.
2. Start with one worker, then at most two; record aggregate and per-component CPU, peak memory, process count, elapsed time, and model usage. Do not run a distribution build or local inference merely to benchmark the coordinator.
3. Disconnect the client while the server remains available; reconnect from the selected phone channel and inspect actual task status and outputs.
4. Reject a consequential action and prove no corresponding persisted change occurred. Cancel a task and verify its workers/tool processes stop rather than merely changing the UI status.
5. After separate approval for a destructive lifecycle probe inside disposable infrastructure, interrupt/restart the trial runtime. Verify checkpoint recovery, no silent work loss, and no duplicate external effects. Conversation history alone does not pass this test.
6. Attempt a forbidden filesystem/control-plane action. A denial must be enforced by the boundary, not explained after the action succeeded.

**Experiment B — Can a narrowly approved browser task use a session without granting the swarm personal authority?**

1. Use a local synthetic page/account and non-sensitive records. Prove observation and explicitly permitted actions before involving a real session.
2. Attempt a denied mutation and a prompt-injection instruction. Verify the application-side data/action log, not only the assistant's response or screenshot.
3. Test revocation with a queued/in-flight action. Document what can still complete and what cannot be undone.
4. Only after passing the agreed boundary tests, obtain separate authorization for one named real account/session, the exact task, allowed operations, and observer availability. Do not copy cookies or extract credentials.
5. If browser control cannot perform the chosen workflow, evaluate full-desktop access as a separate high-risk step. Verify the actual compositor/session backend and the much broader authority before enabling it.

Failure does not authorize installing another orchestrator, broadening permissions, or retrying indefinitely. Record the result, retain evidence, and return to the operator for the affected decision.
