Keep original games on `rog` under `/run/media/library/roms`. Copy selected games to a playing device; do not move originals or synchronize deletions. This is a compatibility plan, not an installation or transfer tool.

## Files are not interchangeable

- Multi-disc games get a `<title>.m3u` playlist next to the disc folders (since ROMHarbor v0.1.10); load the `.m3u` so the core can swap discs, and copy the playlist with every disc folder it lists.
- Preserve disc companions: a `.cue` or `.gdi` may reference several tracks. Copy the whole game bundle with relative paths intact, not an isolated `.bin`.
- Verify each emulator's accepted formats before copying. For example, the catalog accepting `.wbfs` for GameCube does not establish that Dolphin can use it as a GameCube image.
- Keep arcade ROM sets matched to their emulator version, including required parent and BIOS archives. Do not automatically extract or rename arcade archives.
- BIOS, firmware and installation packages need platform-specific preparation. A `.cia`, `.nsp` or Vita package is not necessarily a directly playable ROM.
- Use lawfully obtained BIOS, firmware and game files. This delivery neither fetches nor distributes BIOS, keys or credentials.
- Save files remain local for now. Copying ROMs is not save synchronization; no bidirectional sync or conflict handling is configured.

## Transfer choices

| Route | Intended workflow | Preconditions |
| --- | --- | --- |
| Host over SSH/SFTP | Copy a selected file or complete disc bundle from `rog` to the destination's ROM directory | Verified host identity, authorized login and destination path; no new keys or credentials in this delivery |
| Host over HTTP | Destination downloads selected library files | Existing library-serving endpoint must be verified or separately implemented; catalog download jobs are not a library file server |
| Mac over SMB | Read the existing `rog` ROM share and copy locally | Confirm actual share name, access and mount; no new service needed if existing access works |
| KNULLI over network | Copy into `/userdata/roms/<system>/` via a supported service | Device connectivity and enabled SSH/SFTP or SMB must be verified; HTTP receiving is not assumed |
| KNULLI via SD | Copy into the existing game partition's `roms/<system>/`, then safely eject | Identify the correct card and partition first; no formatting, repartitioning or overwrites |
| KNULLI via USB | Inspect the device's supported USB/ADB mode as a fallback | USB permissions alone do not prove working ADB or network access |

After copying to KNULLI, update the game lists. Keep BIOS in the firmware's expected BIOS directory, normally `/userdata/bios`, not mixed into game folders.

### Authorized macm5 installation

The user explicitly authorized declaring and installing RetroArch and Dolphin on `macm5`,
without full system activation or unrelated application upgrades. These casks are declared in
`hosts/macm5/default.nix`, merging with the shared list. Both applications initially installed
successfully; binary inspection found that the `retroarch` cask was Intel-only, while Dolphin
2609b includes arm64. The declaration was corrected to `retroarch-metal`, whose official download
is universal. Replacement installation succeeded: Homebrew reports `retroarch-metal` 1.22.2 and
`dolphin` 2609b; `lipo -archs` confirms both application executables contain `arm64` and `x86_64`.
This proves installation and binary architecture, not successful gameplay or core availability.

The targeted Homebrew command disables automatic updates, cleanup, installed-dependent checks
and upgrades of existing packages. No `darwin-rebuild`, `brew upgrade`, ROM transfer or game
launch is part of this installation. No `--zap` cleanup is used when replacing the initial cask.
Core installation and controller/gameplay testing remain separate pending checks.

The cask-list evaluation passes on the current Linux host. Full Darwin system evaluation already
failed before this change because `gentle-ai-assets` requires an aarch64-darwin build during
evaluation; this is not evidence that the complete Mac system closure has been verified.

1. Verify one destination's actual installed emulators and choose an already-owned test game.
2. Confirm its complete file bundle, BIOS needs and destination path.
3. With transfer authorization, copy without overwriting existing files and compare file sizes and SHA-256 hashes.
4. Launch the game and check controller, audio and save behavior. A matching hash proves copying, not playability.

The initial map was documentation-only. Subsequent authorized SSH inventory and the targeted
Mac installation are recorded above. No ROM transfers, SD writes, formatting, full activation,
commits or publishing were performed. The separate open-source application remains deferred.
