# SDD Exploration: omarchy-hyprland-regreet-refactor

> **Host**: t14 only (Omarchy/Hyprland laptop)
> **Artifact store**: hybrid (filesystem + engram)
> **Review budget**: 3 rounds

---

## Executive Summary

The t14 Hyprland/ReGreet configuration is split across **two repositories** (nixos-hosts and omarchy-nix) and **two module levels** (NixOS system and Home Manager). The omarchy-nix framework provides the bulk of system-level configuration (Hyprland NixOS module, greetd/regreet wiring, UWSM, XDG portals, PipeWire, fonts) while nixos-hosts provides host-specific overrides and hardware tuning. The configuration is **functional and well-documented** but has **3 areas of redundancy/duplication, 2 fragile custom scripts, and 1 boot-config split** that warrant refactoring.

### 1.2 How Hyprland Is Started

**User session** (post-login):
```
greetd → uwsm start hyprland-uwsm.desktop → uwsm start -F -- start-hyprland
```
- The `hyprland-uwsm.desktop` file is generated by omarchy-nix's `modules/nixos/hyprland.nix`
- When `seamless_boot.enable = true`, a custom override is placed in `environment.systemPackages` to replace the auto-generated desktop file
- t14 does NOT use `seamless_boot` (auto-login) — it uses the ReGreet greeter

**Greeter session** (pre-login):
```
greetd → start-hyprland -- --config /etc/greetd/hyprland.conf
         → exec-once = wayvnc (background) + greetd-regreet-start script
         → greetd-regreet-start: monitor selection → regreet → hyprctl dispatch exit
```

The Hyprland config at `/etc/greetd/hyprland.conf` is generated in omarchy-nix's `system.nix` as a raw string containing:
- Monitor declarations (from `omarchy.greeter.monitors`)
- Cursor theme env vars
- Optional wayvnc exec-once
- exec-once for the greeter launch script
- Input block (keyboard layout/options)
- Misc settings (disable logo, splash, guiutils check)

### 1.3 How ReGreet Is Configured

ReGreet is enabled via the **NixOS `programs.regreet` module** (in nixpkgs), gated by omarchy-nix:
```nix
programs.regreet.enable = lib.mkIf (cfg.greeter.type == "regreet") true;
programs.regreet.settings.GTK.application_prefer_dark_theme = true;
```

The built-in `programs.regreet.enable` default `cage` session is overridden with `lib.mkForce` to use Hyprland directly:
```nix
services.greetd.settings.default_session.command = lib.mkForce
  "${pkgs.hyprland}/bin/start-hyprland -- --config /etc/greetd/hyprland.conf";
```

This approach **bypasses the recommend session file approach** that the NixOS Wiki recommends (using `tuigreet --sessions /run/current-system/sw/share/wayland-sessions`). Instead, it launches Hyprland directly with a custom config.

The regreet program is launched from *within* Hyprland (via exec-once), so:
- Hyprland compositor provides input handling, KMS, cursor
- regreet renders as a Wayland client inside Hyprland
- When regreet exits, `hyprctl dispatch exit` terminates the compositor

## 3. Key Findings and Issues

### 3.1 Greeter Session Architecture (ANTI-PATTERN)

The current approach launches ReGreet inside a custom Hyprland config at `/etc/greetd/hyprland.conf`. This bypasses the standard NixOS session file mechanism (`/run/current-system/sw/share/wayland-sessions`). The NixOS Wiki recommends:

```
services.greetd.settings.default_session.command =
  "${pkgs.tuigreet}/bin/tuigreet --sessions /run/current-system/sw/share/wayland-sessions";
```

For ReGreet, the wiki pattern would be different since ReGreet is a GTK app needing a Wayland compositor. However, the current approach of embedding a bash script into a Hyprland config is fragile:

- The monitor selection script at lines 197-242 of omarchy-nix's system.nix is **140 lines of embedded bash** with custom jq parsing
- Error handling is minimal (most stderr redirected to /dev/null)
- If monitor detection fails silently, the greeter may appear on the wrong screen
- The 10x100ms polling loop for monitor enumeration is a race condition

**Alternative**: Could use `cage` (the default `programs.regreet.enable` session) with wlr-randr for monitor setup, or keep Hyprland but move monitor logic to a proper systemd unit.

### 3.2 Boot Configuration Split

t14 configures boot via `modules/features/boot.nix` (`boot-settings.enable = true`), while omarchy-nix has its own `seamless_boot` module. Both set plymouth, quiet boot params, and console log levels. On t14:
- `seamless_boot.enable = false` (or not set), so omarchy's boot config is inactive
- `boot-settings.enable = true`, so nixos-hosts boot module is active

This split is confusing. The `boot-settings` module wraps standard `boot.*` options in a custom interface without adding much value. It could be:
- **Consolidated**: fold into the host's `default.nix` directly, eliminating the custom module layer
- Or unified with omarchy-nix's seamless_boot

### 3.3 Duplicate/Redundant Custom Code

| Issue | Location | Impact |
|-------|----------|--------|
| `WLR_RENDERER_ALLOW_SOFTWARE,0` env | `hypr/looknfeel.nix` line 22 | No-op on modern Hyprland + AMD iGPU; adds noise |
| Full-opacity blanket windowrule (`mkAfter`) | `hypr/input.nix` lines 24-26 | Overrides ALL of omarchy's per-app opacity rules; comment explains it's intentional but defeats theme system |
| hyprsunset raw config | `hypr/hyprsunset.nix` | Instead of using HM `services.hyprsunset.settings` which exists, uses raw config because omarchy-nix uses raw config too. Should both migrate to HM module |
| waybar custom systemd unit | `home/default.nix` lines 50-70 | HM's `systemd.user.services` could provide cleaner config for Restart behavior |

### 3.4 Fragile Custom Bash Scripts

1. **greetd-regreet-start** (in omarchy-nix system.nix): 140-line embedded bash for monitor selection. Parses JSON with jq, has sleep loops, and relies on Hyprland IPC being ready.

2. **kb-toggle.sh / kb-layout.sh**: Parse Hyprland IPC output with awk. Functional but rely on Hyprland device naming conventions.

3. **mouse-wiggle**: Parses hyprctl cursorpos output. Simple but uses IPC.

### 3.5 t14-Specific Overlay Patches

Two overlay patches in `hosts/t14/default.nix` (xdg-desktop-portal + gvfs) are host-specific. They should arguably:
- Stay where they are (they're specific to the Hyprland + GNOME-apps use case)
- Or move to `modules/hardware/` or `modules/desktop/` if other Hyprland hosts might benefit

## 4. Approaches

### Approach A: Conservative Refactor (Recommended)

**Scope**: Fix only the clearly wrong/obsolete items. Keep the architecture intact.

**Changes**:
1. **Remove `WLR_RENDERER_ALLOW_SOFTWARE,0`** — obsolete on Hyprland 0.54+ with AMD GPU
2. **Consider removing the full-opacity windowrule** or making it configurable — currently it defeats omarchy's theme opacity system
3. **Document the greetd session architecture clearly** — the current approach works but is poorly documented at the architecture level. Add comments explaining WHY it bypasses session files.
4. **Consolidate duplicate boot config** — either remove `boot-settings.enable` and use boot options directly in t14's default.nix, or document why both layers exist.
5. **Simplify the waybar systemd unit** — use HM's declarative systemd options rather than raw unit definition
6. **Research hyprsunset HM module migration** — could both omarchy-nix and nixos-hosts migrate to `services.hyprsunset`?

**Pros**: Minimal risk, preserves working configuration, addresses the most obvious issues
**Cons**: Doesn't fundamentally improve the greeter architecture; leaves the embedded bash script in place
**Complexity**: Low

### Approach B: Greeter Architecture Overhaul

**Scope**: Redesign the greetd ReGreet session to follow best practices.

**Changes**:
1. **Use cage or minimal Sway for ReGreet** instead of full Hyprland — this matches the `programs.regreet.enable` default and removes the need for a custom Hyprland config
2. **Handle monitor selection via systemd service or cage config** rather than embedded bash
3. **Use `/run/current-system/sw/share/wayland-sessions`** for session discovery
4. **Move the greeter start script out of the Hyprland config** into a proper script file

**Pros**: Cleaner architecture, matches NixOS conventions, easier to maintain
**Cons**: Loses Hyprland-specific features at login screen (keyboard layout toggle via Hyprland); cage may not support multi-monitor as well; significant refactor risk
**Complexity**: High

### Approach C: Hybrid — Gradual Cleanup

**Scope**: Clean up custom code classification, remove redundancies, but keep the Hyprland-as-greeter-compositor approach.

**Changes**:
1. All items from Approach A
2. **Extract the greeter start script** from the embedded string in system.nix into a separate `.nix` file or writeShellScriptBin — makes it testable and readable
3. **Add proper error handling** to the monitor selection script (timeouts, fallbacks)
4. **Migrate hyprsunset** to `services.hyprsunset` in omarchy-nix upstream, then remove the t14 raw config
5. **Add session discoverability** — add a comment referencing how the session is wired (or add a wrapper .desktop file)

**Pros**: Balances improvement with stability; most changes are self-contained; fixes can be verified incrementally
**Cons**: Still doesn't use session files; the Hyprland-as-greeter-compositor approach remains
**Complexity**: Medium

---

## 5. Recommendation

**Approach C: Gradual Cleanup**

The configuration is functional and well-tested. The current greeter architecture (Hyprland + regreet) was intentionally chosen over cage to provide keyboard layout switching at the login screen — this is a legitimate requirement that cage cannot fulfill. Replacing it with cage would lose this feature.

The priority should be:
1. **Remove obsolete config** (`WLR_RENDERER_ALLOW_SOFTWARE`)
2. **Consolidate boot configuration** (remove or simplify the `boot-settings` custom module)
3. **Extract the greeter script** from the embedded string into a proper file
4. **Add documentation** explaining the architecture decisions
5. **Migrate hyprsunset** to HM module (requires omarchy-nix upstream change)

## 6. Risks

| Risk | Severity | Mitigation |
|------|----------|------------|
| Greeter breakage during refactor | **High** | The greeter is the ONLY way to log in. Any change must be tested on a spare VT (systemd.mask=greetd.service fallback). Do greeter changes LAST in the refactor sequence. |
| omarchy-nix upstream sync | **Medium** | Changes to omarchy-nix (like hyprsunset migration) need to be merged there first, then the nixos-hosts flake input updated. PR against omarchy-nix first. |
| Boot regression | **Low** | Boot module changes are simple and can be verified via `nixos-rebuild boot` + reboot test. |
| Overlay patch interaction | **Low** | xdp and gvfs patches are isolated and specific. No changes planned. |
