## Issues Found

### CRITICAL
None.

### WARNING

1. **REQ-GS-003: Greeter stderr logs not captured in journal**
   The greeter script correctly implements stderr logging at all phases (7 `echo ... >&2` lines source-verified in omarchy-nix system.nix). However, the deployed system's greetd session does not forward the greeter Hyprland session's stderr to the systemd journal. `journalctl -u greetd -b` shows only PAM messages; `journalctl -b | grep greetd-regreet-start` returns no matches. The script's stderr goes to the greeter session's stderr, which greetd does not persist to journald. The log lines would appear on VT 1 during boot but are not captured for post-hoc debugging.
   **Impact**: Diagnostic logging exists in the script but is not retrievable from the journal after login. The script is correct; the capture path is the gap.
   **Recommendation**: Wrap the greetd session command with `systemd-cat` or configure greetd logging to forward stderr to the journal.

2. **REQ-HC-003: Architecture comment length below spec target**
   The spec scenario requires "a comment block (50+ lines)". The implemented block is 16 lines (omarchy.nix lines 31-46). All 5 required content points are covered (keyboard layout toggle, cage limitation, greetd-to-Hyprland-to-regreet chain, VT escape hatch, ownership boundary). The design (Section 2.6) specified this shorter block. The length deviation is cosmetic -- the content is complete and concise.
   **Impact**: None functional. A future maintainer gets all required information in a more compact form.

3. **Phase 5.2: VT fallback boot test not performed**
   The `systemd.mask=greetd.service` boot test requires manual interaction at the systemd-boot menu (press `e`, append kernel param, boot). This was not executed during verification. The documentation IS in place (omarchy.nix lines 44-46), and the greeter IS working (user logged in successfully at 23:32:10), but the recovery path was not empirically tested.
   **Impact**: The VT fallback is a standard systemd mechanism (`systemd.mask=`), not custom code, so the risk of it not working is very low. However, it remains empirically unverified.

### SUGGESTION

1. **REQ-HC-002 design deviation documented**: The spec requested moving the opacity windowrule from `extraConfig` to `settings.windowrule` (declarative path), but the implementation keeps it in `extraConfig` with `lib.mkAfter`. The design (Section 2.2) justifies this: `mkAfter` ordering is required to defeat omarchy's per-app opacity rules that use `-default-opacity` tags. The `let forceFullOpacity` boolean gate satisfies the "configurable" requirement. The spec explicitly allowed a `let` boolean fallback. Consider updating the spec to reflect the design-validated approach.

2. **REQ-WB-001 spec premise correction**: The spec assumed "Home Manager's `programs.waybar` module already generates a `systemd.user.services.waybar` unit with sensible defaults." The design verified this is incorrect for this stack -- omarchy-nix's waybar HM module installs only the package + static config files, not a systemd unit. Consider updating the spec to reflect that t14's unit is the sole definition.

3. **Unrelated commit interleaved**: Commit `739374a` (Materia-dark-compact GTK override + Qt Adwaita Dark) was interleaved between Phase 2.2 and Phase 4.1 commits. This is outside the scope of this SDD change but means the git history is not cleanly separated. The omarchy.nix diff (36 lines) includes both the architecture doc (this change) and the GTK/Qt overrides (unrelated change). Consider noting this in the PR description if a PR is created.
