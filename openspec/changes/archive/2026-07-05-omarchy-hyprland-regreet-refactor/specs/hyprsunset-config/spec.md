# Delta Spec: hyprsunset-config

> Domain: hyprsunset migration from raw config to Home Manager module.
> Host: t14 (nixos-hosts side) + omarchy-nix upstream (PR dependency).
> Source files: `hosts/t14/home/hypr/hyprsunset.nix` (nixos-hosts), `modules/home-manager/hyprsunset.nix` (omarchy-nix).

---

## MODIFIED Requirements

### REQ-HS-001: Migrate hyprsunset from xdg.configFile to services.hyprsunset

**What**: The hyprsunset configuration in `hosts/t14/home/hypr/hyprsunset.nix` SHALL be migrated from `xdg.configFile."hypr/hyprsunset.conf"` (raw text blob) to the declarative `services.hyprsunset.settings` Home Manager option.

**Why**: Home Manager provides `services.hyprsunset` module (available in nixpkgs unstable) with declarative `settings` option that generates the config file and systemd user service. The current approach uses `xdg.configFile` to generate the config and relies on omarchy-nix's manually-defined `systemd.user.services.hyprsunset` unit. Using the HM module eliminates the raw config blob, provides option validation, and deduplicates the systemd unit definition.

**Dependency**: This change REQUIRES an upstream omarchy-nix PR to migrate `modules/home-manager/hyprsunset.nix` from raw config to `services.hyprsunset.settings` first. Without the omarchy-nix migration, two systemd units would conflict (the HM module generates one, and omarchy-nix defines another at the same path). The omarchy-nix PR:
1. SHALL replace `xdg.configFile."hypr/hyprsunset.conf".text` with `services.hyprsunset.settings` in the HM module
2. SHALL remove the manual `systemd.user.services.hyprsunset` definition (the HM module generates it)
3. After merging, the nixos-hosts flake input SHALL be updated (`nix flake update omarchy-nix`)

**Migration mapping**: The current `xdg.configFile` content:

```
profile { time = 07:00 identity = true }
profile { time = 18:00 temperature = 4500 }
profile { time = 19:30 temperature = 4000 }
profile { time = 21:00 temperature = 3500 }
profile { time = 23:00 temperature = 3000 }
```

SHALL become:

```nix
services.hyprsunset.settings = {
  profile = [
    { time = "07:00"; identity = true; }
    { time = "18:00"; temperature = 4500; }
    { time = "19:30"; temperature = 4000; }
    { time = "21:00"; temperature = 3500; }
    { time = "23:00"; temperature = 3000; }
  ];
};
```

Note: The two duplicate `profile { time=07:00 identity=true }` blocks (a copy-paste artifact in the source file) SHALL be collapsed into one in the declarative format. Hyprsunset ignores duplicate identity profiles.

#### Scenario: Declarative config generates valid hyprsunset.conf

- **Given** `services.hyprsunset.settings` is configured with 5 profiles
- **When** Home Manager activation writes the hyprsunset config file
- **Then** the generated `~/.config/hypr/hyprsunset.conf` SHALL contain valid TOML-equivalent format
- **And** hyprsunset SHALL parse it without errors
- **And** the progressive warming schedule SHALL be identical to the old raw config (07:00 identity, 18:00 at 4500K, 19:30 at 4000K, 21:00 at 3500K, 23:00 at 3000K)

#### Scenario: systemd user service is generated by HM module

- **Given** `services.hyprsunset` is enabled via the HM module
- **When** Home Manager activation generates systemd user units
- **Then** `systemd/user/hyprsunset.service` SHALL exist
- **And** it SHALL have `PartOf = graphical-session.target`
- **And** it SHALL have `After = graphical-session.target`
- **And** it SHALL have `WantedBy = graphical-session.target`
- **And** it SHALL use Restart behavior appropriate for a blue-light filter daemon

#### Scenario: No duplicate systemd unit conflict

- **Given** the omarchy-nix upstream HM module no longer defines `systemd.user.services.hyprsunset` manually
- **And** the nixos-hosts flake input points to the updated omarchy-nix commit
- **When** `nix flake check --no-build` is run for t14
- **Then** no systemd unit name collision SHALL be reported
- **And** no "option defined multiple times" warning SHALL appear for `systemd.user.services.hyprsunset`

#### Scenario: t14 host-specific profiles are preserved

- **Given** the t14 user wants progressive warming (not just the omarchy-nix default single identity profile)
- **When** `services.hyprsunset.settings.profile` is configured with 5 entries
- **Then** the profile list SHALL be the t14-specific schedule
- **And** the omarchy-nix default profile (single identity at 07:00) SHALL be overridden

#### Scenario: omarchy-nix upstream PR is required first

- **Given** the omarchy-nix `modules/home-manager/hyprsunset.nix` still uses raw `xdg.configFile` + manual systemd unit
- **When** the nixos-hosts t14 config attempts to use `services.hyprsunset`
- **Then** Home Manager SHALL fail with a conflict error because two modules define `systemd.user.services.hyprsunset`
- **Therefore** the omarchy-nix PR SHALL be merged and the nixos-hosts flake input updated BEFORE this nixos-hosts change is applied

## ADDED Requirements

### REQ-HS-003: Validate hyprsunset profile format at build time

**What**: When declarative `services.hyprsunset.settings` is used, the Home Manager module SHALL validate that profile entries have valid `time` and `temperature` or `identity` fields.

**Rationale**: The raw config approach was a text blob with no validation. Typos in time format or temperature values would only be caught at runtime when hyprsunset failed to parse the config. The HM module provides schema validation that catches errors at build time.

#### Scenario: Invalid profile time format is caught at build time

- **Given** a profile entry has `time = "25:00"` (invalid hour)
- **When** `nix flake check --no-build` is run
- **Then** the HM module SHALL report an error (or hyprsunset at startup SHALL reject the config)
- **And** the build SHALL NOT silently generate a broken config file

#### Scenario: Valid profiles pass validation

- **Given** all profile entries have valid `time` (HH:MM, 00:00-23:59) and valid `temperature` (1000-10000) or `identity = true`
- **When** `nix flake check --no-build` is run
- **Then** the validation SHALL pass
- **And** the config file SHALL be generated successfully
