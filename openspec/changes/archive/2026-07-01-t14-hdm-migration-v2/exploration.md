# Exploration: t14-hdm-migration-v2

## Current State

T14's monitor stack is a 3-layer, ~290-line fragile contraption:

### Layer 1 — `hosts/t14/home/scripts/monitor-lid-validator.sh` (71 lines)
- Polling bash daemon that reads `/proc/acpi/button/lid/LID*/state` every 2s
- Calls `hyprctl keyword monitor ...` on state change
- Calls `hyprctl reload` (causes flicker)
- Persists state to `~/.config/hypr/settings.conf` via `printf`

### Layer 2 — `hosts/t14/home/hypr/monitors.nix` (86 lines)
- Static `monitor=...` directives wrapped in `# hyprlang if ENABLE_LAPTOP` / `# hyprlang endif`
- Two complete copies of the layout (y=420 and y=0) gated by the persisted state
- `mkWorkspaceRules` for cyclic mod-3 distribution across 20 workspaces
- Two 300-character `bindl` directives that fire on `switch:on:.*[Ll]id.*` and write to `settings.conf` + call `hyprctl keyword monitor ...` again
- GDK_SCALE=1 env var (must keep)

### Layer 3 — `hosts/t14/home/default.nix` (~106 lines, relevant fragments)
- `home.activation.seedHyprSettings` — seeds `settings.conf` on first run
- `xdg.configFile.".../udev-settle.conf"` — `udevadm settle` drop-in for Hyprland
- `systemd.user.services.monitor-lid-validator` — runs the daemon after `graphical-session.target`
- `home.file.".local/bin/monitor-lid-validator.sh"` — deploys the script

### Anchor conditions
- `omarchy.hyprland.lidSwitch.enable = false` (line 158 of `hosts/t14/default.nix`) — omarchy's own `bindl` is OFF, so only the T14 bindl/daemon wrote state
- `omarchy.greeter.*` block (regreet) is a separate Hyprland session, must remain untouched
- `omarchy.monitors = [ "eDP-1,preferred,auto,1" ]` (line 153) — only eDP-1 by default; externals come from our T14 config
- `omarchy-hyprland-monitor-watch` (socat listener from omarchy-nix) calls `hyprctl reload` on `monitoradded>>` events — orthogonal but races with HDM

## Tools Research

### HyprDynamicMonitors (HDM)

- **NixOS availability**: `hyprdynamicmonitors 1.4.0` in nixpkgs unstable (`pkgs.hyprdynamicmonitors`).
- **Module availability**: Upstream flake exposes BOTH `nixosModules.default` and `homeManagerModules.default`. nixpkgs package itself only provides the binary; modules come from the flake input. The HM module writes the TOML to `~/.config/hyprdynamicmonitors/config.toml` (NOT to the destination file) and creates the user systemd services.
- **Profile matching** (verified via official docs + examples in upstream repo):
  - `name` field → matches Hyprland connector name (`eDP-1`, `DP-1`, `HDMI-A-1`).
  - `description` field → matches Hyprland `description` string (EDID-based, stable across kernel updates that change connector numbers).
  - `match_name_using_regex` / `match_description_using_regex` → boolean flags, default `false`. Exact string match by default.
  - `monitor_tag` → optional label, only used in Go templates.
  - All `required_monitors` in a profile MUST be present for the profile to match.
- **Scoring** (verified):
  - Default weights: `name_match = 10`, `description_match = 5`, `power_state_match = 3`, `lid_state_match = 2`.
  - **Profile with highest score wins.** Ties broken by **last profile defined** in the TOML.
  - For our 4-monitor + lid scenario:
    - `docked_lid_open`: eDP-1 (name 10) + 3 externals (desc 5×3) + lid=Opened (2) = **27**
    - `docked_lid_closed`: same monitors + lid=Closed (2) = **27**
    - `undocked_lid_open`: eDP-1 (name 10) + lid=Opened (2) = **12** (only matches if externals absent)
    - `undocked_lid_closed`: eDP-1 (name 10) + lid=Closed (2) = **12**
  - Scoring correctly disambiguates docked vs undocked because undocked profiles REQUIRE only eDP-1 (no externals) and docked profiles REQUIRE all 4 monitors.
- **Fallback**: `[fallback_profile]` (NOT `[profiles.fallback]`). Applies only when NO other profile matches.
- **Explicit coordinates**: **YES — fully supported in static profiles.** Static profiles are plain Hyprland config files. The example `monitor=eDP-1,2880x1920@120,0x0,2.0,vrr,1` shows full control over name, mode, position, scale, vrr, transform. The T14's `monitor=desc:AOC 24P1W1 OTNQ4HA000101,1920x1080@60,0x420,1,transform,1` syntax is valid Hyprland syntax and will pass through HDM unmodified.
- **Lid events**: Activated by `--enable-lid-events` flag (passed via `extraFlags`). HDM subscribes to `org.freedesktop.UPower` D-Bus signal `PropertiesChanged` on `/org/freedesktop/UPower` and queries `LidIsClosed` property. Default values match standard UPower installations. **UPower MUST be enabled** — it is (`modules/hardware/amd-laptop.nix:25`).
- **`prepare` service**: Strips stale `monitor=...,disable` lines from previous HDM output before Hyprland starts. The HM module creates a `hyprdynamicmonitors-prepare.service` (Type=oneshot, RemainAfterExit=yes) bound to `graphical-session-pre.target` with `Before=graphical-session-pre.target` and `default.target`. Critical for first-boot safety.
- **Key examples found**:
  - `examples/lid-states/config.toml` — minimal lid open/closed with single monitor. The model we follow.
  - `examples/scoring/config.toml` — shows how scoring weights disambiguate 3 profiles that all match. Identical shape to our scenario.
  - `examples/fallback/config.toml` — shows `[fallback_profile]` syntax (v1 design used `[profiles.fallback]` which would have caused issues).
  - `examples/full/config.toml` — exhaustive reference for all options.
  - `examples/lid-states/hyprconfigs/closed.conf` — `monitor = eDP-1, disable` is their example, but we use `-30000x0` to dodge Hyprland #1274 (the v1 design correctly identified this).
- **Native IPC, no `hyprctl reload`**: HDM uses `hyprctl keyword monitor` directly via the Hyprland IPC socket, NOT `hyprctl reload`. No flicker.

### hyprdocked

- **NixOS availability**: **NOT in nixpkgs** (searched `hyprdocked` — zero results). Would require a custom flake input.
- **Capabilities** (from exa search of `github.com/dsrosen6/hyprdocked`): Listens for Hyprland socket2 monitor add/remove events + UPower lid events. Configured via `~/.config/hypr/hyprdocked.yaml`. **Requires Hyprland v0.55+** because it uses `hyprctl eval` with Lua to manage monitors. Integrates with hypridle via `hyprdocked idle` / `hyprdocked resume` for suspend coordination.
- **Lid handling**: Native — uses UPower/lid directly.
- **Comparison vs HDM**:
  - **Disadvantage**: NOT in nixpkgs → would need a custom flake input + manual build. Adds maintenance burden.
  - **Disadvantage**: Uses `hyprctl eval` (Lua) which the v1 postmortem identified as a Hyprland 0.55 bug source.
  - **Disadvantage**: YAML config — less typed than HDM's TOML + Nix module.
  - **Advantage**: Integrates directly with `hypridle` for idle/suspend coordination. HDM has no equivalent.
  - **Advantage**: Smaller surface area — single Go binary ~5MB vs HDM's larger Go binary with TUI.
  - **Net**: HDM is a strictly better fit. The hypridle integration is a non-issue because T14 already uses omarchy's hypridle setup independently.

### Other tools discovered

- **hyprland-dock-undock-automation** (EndoliteMatrix): Single bash script using `socat` on Hyprland socket2 + `hyprctl eval` + off-screen park at `-30000x0`. **No upstream package.** Re-implements the same pattern we have today (just with `socat` instead of `/proc/acpi` polling). **Not a migration candidate** — would be more code, not less.
- **hyprpier** (jakeb-grant): TUI-based, requires `sudo` for udev rules to detect Thunderbolt docks. Overkill for T14.
- **hyprdock** (DashieTM, crates.io): Not in nixpkgs, requires `acpid`, last release 2023. Dead project.
- **kanshi / shikane**: Generic Wayland managers. Hyprland-specific tools preferred.

## Known Issues Validation (from v1 POSTMORTEM)

| Issue | Original Claim | Validated? | Reality |
|-------|---------------|------------|---------|
| 1 — Tilde in `source` | Hyprland does not expand `~` in `source` directives | **YES** | Confirmed. Use `config.home.homeDirectory` to construct absolute paths. |
| 2 — `home.file` clobber | HM symlink + HDM write = "would be clobbered" on next activation | **YES (with caveat)** | The HM module deploys `config.toml` (the SOURCE config, NOT the destination). HDM writes to the `destination` field, which is by default `~/.config/hypr/monitors.conf`. These are SEPARATE files. The clobber only happens if you point HDM's destination at a path that HM also manages. **In our design: HDM destination = `~/.config/hypr/config.d/99_autogenerated-monitors.conf` which is NOT HM-managed. Safe.** |
| 3 — `name = "desc:..."` | `name` field never matches `desc:` syntax | **YES** | The `name` field matches Hyprland connector name (`eDP-1`, `DP-1`). The `description` field matches the EDID description. Use `description = "AOC 24P1W1 OTNQ4HA000101"` for externals. The v1 **design** used the correct field — the postmortem refers to a code-change during implementation that was different from the design. |
| 4 — `[profiles.fallback]` | Fallback must be `[fallback_profile]` | **YES** | Confirmed in all upstream examples. `[profiles.fallback]` is a regular profile with no conditions → always matches → wrong selection. |
| 5 — Missing scoring | Without weights, wrong profile selected | **YES** | Confirmed via scoring example. Multiple profiles can match the same state (e.g., docked + lid open has 2 candidates: `docked_lid_open` and `undocked_lid_open` if eDP-1 is also connected). Default weights disambiguate by total monitor count, but explicit `[scoring]` block is best practice. |
| 6 — Workspace rule merging | Two `default:true` for same workspace breaks Super+1/2/3 in Hyprland 0.55 | **YES** | Confirmed. v1 design **did not** apply the fix. The `mkWorkspaceRules` in `monitors.nix` binds ws 1-3 to externals AND `extraConfig` binds them to eDP-1 → two `default:true` → Super+1/2/3 fail. **v2 fix: filter `w > 3` from `mkWorkspaceRules`.** |
| 7 — Flicker from `hyprctl reload` | Reload causes visual reset on every cycle | **N/A for HDM** | HDM uses `hyprctl keyword monitor ...` via native IPC, NOT `hyprctl reload`. The `omarchy-hyprland-monitor-watch` socat listener (from omarchy-nix, separate daemon) DOES call `hyprctl reload` on `monitoradded>>` events — this is orthogonal but could race with HDM's monitor writes. Document as known interaction. |
| 8 — `moveworkspacetomonitor` | Wrong syntax in v1 attempts (comma vs space) | **N/A** | HDM handles all positioning via `monitor=` directives, not dispatcher commands. |
| 9 — Connector instability | DP names change across kernel updates | **YES** | Confirmed. Use `description` (EDID-based, stable) for externals. eDP-1 is stable across kernel updates. |

## Approaches

### 1. HyprDynamicMonitors with static profiles (HDM, primary candidate)

- **Description**: Replace the 3-layer stack with HDM v1.4.0. Four static profiles (docked_lid_open, docked_lid_closed, undocked_lid_open, undocked_lid_closed) + `[fallback_profile]`. Each profile points to a static `.conf` file with exact `monitor=` lines (including explicit y=420 dead-zone coordinates and `-30000x0` off-screen park for eDP-1). HDM scoring disambiguates the 4-way state. Lid events via UPower D-Bus (already enabled). Profile matching by `description` (stable EDID).
- **Pros**:
  - Eliminates ~290 lines of fragile bash + hyprlang + bindl.
  - In nixpkgs (1.4.0), well-maintained (351 stars, v1.4.0 from 2025-12-01), has both NixOS and HM modules.
  - Event-driven: Hyprland socket2 + UPower D-Bus, no polling.
  - Native IPC `hyprctl keyword monitor` (no `hyprctl reload` flicker).
  - All known v1 bugs (1, 3, 4, 5, 6) are addressable with documented syntax.
  - Dead-zone y=420 fully supported (static configs are raw Hyprland syntax).
  - Off-screen eDP-1 park `-30000x0` works (avoid Hyprland #1274).
  - Description-based matching handles connector instability.
  - Profile scoring correctly disambiguates the 4-state matrix.
- **Cons**:
  - 5 new files to maintain (`config.toml` + 4 hyprconfigs + fallback) — but all declarative, no logic.
  - HDM v1.4.0 is recent (Dec 2025) — risk of undiscovered bugs. Mitigation: keep old daemon script commented out in git for one cycle.
  - Requires explicit `extraFlags = [ "--enable-lid-events" ]` — easy to forget.
  - Race with `omarchy-hyprland-monitor-watch` socat listener: both react to `monitoradded>>`. Need to confirm omarchy's listener does no-op or harmless reload when HDM also fires.
  - UPower required (already enabled — no change needed).
- **Effort**: **Low** — HM module wiring is 5 lines, TOML is ~50 lines, 4 hyprconfigs are ~15 lines each, Nix wiring is 1 import. The hard part (workspace filter) is a one-line Nix change.
- **Dead-zone support**: **YES** — static profile can contain any Hyprland monitor directive, including `monitor=desc:AOC 24P1W1 OTNQ4HA000101,1920x1080@60,0x420,1,transform,1`.

### 2. hyprdocked (fallback candidate, not in nixpkgs)

- **Description**: Replace the 3-layer stack with hyprdocked (Rust, dsrosen6/hyprdocked). YAML config + systemd user service. Requires Hyprland ≥0.55 + Lua.
- **Pros**:
  - Native hypridle integration (`hyprdocked idle` / `hyprdocked resume`).
  - Small, focused: only does lid + monitor events.
- **Cons**:
  - **NOT in nixpkgs** — requires custom flake input + manual build, no upstream support.
  - Uses `hyprctl eval` (Lua) which the v1 postmortem identified as a Hyprland 0.55 bug source.
  - YAML config has no type-checking or Nix integration.
  - Less mature than HDM (smaller community).
  - Cannot reuse our existing v1 design — start from scratch.
- **Effort**: **High** — need to package, write flake input, write systemd unit, YAML config, validate against Hyprland 0.55+ Lua quirks.
- **Dead-zone support**: **YES** — hyprdocked accepts raw Hyprland `monitor=` directives.

### 3. Custom socat + hyprctl eval (rebuild current design on top of socket2)

- **Description**: Replace polling bash with `socat` on socket2 + `hyprctl keyword monitor ...` (no reload), driven by a tiny shell loop. Same shape as `EndoliteMatrix/hyprland-dock-undock-automation` but adapted.
- **Pros**:
  - No new dependencies — uses only what we have.
  - Eliminates `/proc/acpi` polling.
- **Cons**:
  - Still 100+ lines of custom shell. Same fragility the v1 attempt was trying to escape.
  - Race conditions on rapid dock/undock are harder to avoid without debouncing.
  - Not a NixOS-managed solution.
- **Effort**: **Medium** — port current daemon to use socket2 + UPower, remove polling.
- **Dead-zone support**: **YES** — direct `hyprctl keyword monitor`.

## Recommendation

**Approach 1: HyprDynamicMonitors with static profiles.**

Evidence:
- All 4 layout states are exactly representable as 4 static TOML profiles + fallback.
- Dead-zone y=420 is a raw Hyprland `monitor=` directive — fully supported by HDM static profiles (verified via `examples/lid-states/hyprconfigs/closed.conf` and `examples/full/hyprconfigs/laptop-only.conf`).
- Off-screen eDP-1 park at `-30000x0` is identical syntax.
- Scoring matrix works: 4-state disambiguation by monitor count + lid match (verified via Go source `internal/matchers/matcher.go` and `examples/scoring/config.toml`).
- All 6 v1 bugs are addressable with documented syntax (1: absolute path, 2: separate destination from HM-managed paths, 3: use `description` for externals, 4: `[fallback_profile]`, 5: explicit `[scoring]` block, 6: filter `w > 3` in `mkWorkspaceRules`).
- HDM is the ONLY viable candidate that is in nixpkgs and event-driven.

Approaches 2 and 3 fail the "no new dependencies" / "less code than current" requirements. The v1 attempt failed because the design and implementation diverged (BUG 3) plus the workspace filter (BUG 6) was not applied — not because HDM itself is unsuitable. v2 fixes all 6 bugs by construction.

## Risks

- **R1 — `omarchy-hyprland-monitor-watch` race**: omarchy-nix's socat listener calls `hyprctl reload` on `monitoradded>>` events. HDM also reacts to the same event. Both run as user services after `graphical-session.target`. The race is benign if HDM writes win (HDM uses IPC, reload re-parses all monitor= blocks including the latest HDM output). Could cause one extra reload. **Mitigation**: leave `omarchy-hyprland-monitor-watch` as-is; observe for flicker on first dock/undock; if problematic, add a small `monitoradded` debounce in HDM's `debounce_time_ms` (1500ms default is already long enough).
- **R2 — UPower regression**: HDM with `--enable-lid-events` requires UPower. UPower is already enabled in `modules/hardware/amd-laptop.nix`. If that module is removed or its UPower block is overridden by a future omarchy-nix version, HDM lid events silently fail. **Mitigation**: add a `services.upower.enable = true` assertion in `hosts/t14/default.nix` (or document the dependency in the commit message).
- **R3 — Connector description changes**: EDID-based descriptions can change if a monitor firmware updates or is replaced. Currently `AOC 24P1W1 OTNQ4HA000101` is the serial-number-suffixed description. If the monitor is replaced, the profile silently stops matching and falls through to `[fallback_profile]` (which uses `monitor=,preferred,auto,1` — generic). **Mitigation**: fallback covers this case. User can re-run `hyprctl monitors -j` and update TOML.
- **R4 — v1 design re-introduced**: easy to copy from `archive/FAILED-2026-06-29-hyprdynamicmonitors-migration-v1/` by accident. The archive is correct as a learning artifact but must not be used as a template. **Mitigation**: in the proposal, explicitly call out which v1 patterns to AVOID and WHY (with file paths).
- **R5 — Workspace filter breaks waybar monitor module**: waybar reads `hyprctl monitors -j` and shows whichever monitor the cursor is on. Filtering ws 1-3 from `mkWorkspaceRules` only changes the default-workspace binding, not the monitor selection. **Mitigation**: waybar is unaffected; confirm during manual test.

## Ready for Proposal

**YES.** All technical questions are answered. The 6 v1 bugs are mapped to specific fixes in v2. The dead-zone y=420 is confirmed supported. The 4-state matrix is confirmed representable with HDM scoring. UPower is already enabled. The recommendation is unambiguous: HDM v1.4.0 with static profiles, address all 6 v1 bugs by construction.
