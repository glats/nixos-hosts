### Approaches

1. **Direct single-stack v4 migration with isolated candidate validation** — prepare one coherent binary/assets/ODD graph replacement, preserving 2.0.14 and narrowly adapting existing V2 contracts; prove it in disposable configuration before authorized rog cutover, then all four hosts.
   - Pros: matches accepted upstream ODD target, no V1/forever dual stack, rollback retains history and generations.
   - Cons: cross-consumer graph/prompts and native receipt parity need real proof; cannot safely be only a pin bump.
   - Effort: Medium–High.
2. **Wholesale vanilla v4 assets plus runtime/SDK change** — install upstream 2.0.4-targeted plugins and separately upgrade CLI to reproduce upstream 2.0.19 harness.
   - Pros: closer to upstream fixture and fewer local transport differences eventually.
   - Cons: broadens unapproved CLI/SDK scope, still lacks Linux/real-model proof, may break Engram/RTK/host hooks; exact installer SDK pin is not runtime compatibility proof.
   - Effort: High; only reconsider after a named compatibility failure.
3. **Remain on current v2.5 while proving candidate** — temporary preparation state, not a second installed production stack.
   - Pros: preserves the currently working orchestrator and receipts while avoiding premature self-removal.
   - Cons: no completed upgrade until gates pass; indefinite deferral does not satisfy accepted direction.
   - Effort: Low as a staging posture, not final architecture.
