## Exploration: response formatting rules for AI agents

### Current State
- OpenCode and Claude Code both load instruction fragments generated by Nix activation scripts.
- `shared/opencode/runtime-config.nix` (221–227) and `shared/claude-code.nix` (271–277) concatenate `config.home.ai-assets.agentsMdSources` into `~/.config/opencode/AGENTS.md` and `~/.claude/CLAUDE.md` respectively, overwriting (`>`) on every activation — direct edits are futile.
- `shared/ai-assets.nix` (32–39) defines `agentsMdSources` default = `[ "${pkgs.gentle-ai-assets}/share/gentle-ai/AGENTS.md" ./rules/explore-mcp.md ]`. One added path reaches both tools.
- Generated files currently identical (42 lines / 3306 bytes each). Upstream gentle-ai assets contain no response-formatting rules.
- `opencode.json` is generated with `instructions = []` (runtime-config.nix:89) — a separate, OpenCode-only channel.

### Affected Areas
- `shared/ai-assets.nix` — append one fragment path to the `agentsMdSources` default.
- `shared/rules/output-format.md` (new) — the response-format instruction fragment.
- `~/.config/opencode/AGENTS.md` and `~/.claude/CLAUDE.md` — generated; receive the appended section on activation.

### Approaches
1. **A — New fragment + one line in `agentsMdSources`**
   - Pros: model-agnostic (plain instruction text, no provider coupling); declarative in Nix; reaches both tools from one list; lowest maintenance; mirrors existing `explore-mcp.md` pattern.
   - Cons: adherence is prompt-instruction only, not enforced; appended to a generated file amid other context, so dilution is possible.
   - Effort: Low

2. **B — `opencode.json` per-agent prompt override**
   - Pros: can target the orchestrator/persona precisely; stronger placement than a fragment appended to a larger file.
   - Cons: OpenCode-only (does not cover Claude Code); json is regenerated from `runtime-config.nix`, so the edit still lives in Nix; per-agent/per-host duplication across providers.
   - Effort: Medium

3. **C — OpenCode plugin hook (`experimental.text.complete`)**
   - Pros: runtime enforcement (can block/rewrite verbose replies); model-agnostic.
   - Cons: experimental API, fragile across OpenCode upgrades; post-processing prose is brittle (risks mangling code blocks/diffs); OpenCode-only; high maintenance.
   - Effort: High

4. **D — Rely on on-demand caveman skill**
   - Pros: zero config; already present.
   - Cons: not default (requires explicit invocation); per-invocation only; no Claude Code equivalent auto-trigger; not declarative.
   - Effort: None (does not meet the goal)

### Recommendation
Approach A. A single short fragment appended to `agentsMdSources` is the only option that is model-agnostic, declarative-in-Nix, and reaches both tools at minimal maintenance cost. The evidence decides the wording, not the strict Anthropic block: the verbatim `avoid_excessive_markdown_and_bullet_points` block is confirmed to overcorrect (tomerbr1's tested "poet problem" — the model refused lists even when requested), so the fragment must use shape-matching ("Match the shape of the answer to the shape of the question…") rather than an absolute anti-list prohibition. Two further evidence-driven rules: lead with the answer, and write the fragment itself as flowing prose (Anthropic's "match your prompt style to the desired output" — a bulleted rule list would teach bullet output).

### Risks
- Poet overcorrection (medium) — mitigated by shape-matching plus "lists allowed when enumerable or explicitly requested."
- Instruction dilution (medium) — mitigated by keeping the fragment ~10–15 lines, imperative, appended.
- "Be concise" alone is ineffective — the fragment must pair explicit format constraints with the brevity goal, not rely on bare conciseness.

### Ready for Proposal
Yes. The proposal already matches Approach A with shape-matching wording and correct affected areas. No structural revision is needed. The spec phase should incorporate: (1) the fragment written in prose form (self-demonstrating), (2) an explicit shape-matching directive, (3) a lead-with-answer rule, and (4) an exemption for code blocks, diffs, and command output.
