An outbound-only target can connect to rog only if rog has a reachable inbound path, or an explicitly accepted outside intermediary provides one. If rog is also unreachable behind CGNAT and there is no intermediary, none of the self-hosted choices below solves that topology. If both devices share the home LAN, ordinary SSH or a reachable jump host may suffice; reverse tunnels are needed for targets that leave that LAN or otherwise cannot accept inbound connections.

### Approaches

All self-hosted transports require reachable rog while it is powered on. For the confirmed MVP, only macm5-to-rog needs a network tunnel: the authorized agent/operator on rog consumes an explicit rog loopback reverse listener with ordinary SSH. A second HTTPS operator tunnel, STCP visitor, or public reverse SSH port is unnecessary. Keep publishing authentication separate from final Mac SSH key authentication and host verification. ### Risks

- **Physical availability:** all rog-mediated SSH disappears while rog is off; no tunnel reaches a sleeping/off macm5. The user already has remote rog power-on capability; do not implement, test, or redesign it as part of this change. The enabled client reconnects after rog's network/relay endpoint becomes available, not necessarily at the instant power is applied. Existing WOL evidence does not establish the mechanism of the user's capability. No existing SSH session survival is promised.
- **Security boundary:** user approved trusted macm5 client operation: independently revocable per-host publishing credential, rog-enforced designated loopback listener and denial of other publications/listeners/normal forwarding; fixed managed Mac configuration forwards only `127.0.0.1:22`. The relay cannot independently attest a malicious Mac endpoint. Final SSH key/host-key authentication remains independent. rog's disabled firewall makes accidental wildcard listeners dangerous. Existing password-enabled Linux SSH needs deliberate exposure review, not unrequested global modification.
- **Managed workplace:** macm5 has corporate CA/security-agent context (`hosts/macm5/default.nix:20-36`). HTTPS/WSS compatibility is not proof of permission or successful office traversal. Require administrator-authorized access and real native tests; do not weaken TLS verification or disguise traffic to evade policy. TLS interception can terminate WS or defeat mTLS; Chisel's inner pinned key adds server authentication but does not override network policy.
- **DNS/CDN:** wildcard coverage and existing Cloudflare-fronted history are helpful, not a public ingress guarantee. Adding a subdomain may depend on an outside CDN even without a VPS. WebSocket idle limits/restarts and source address changes require reconnect testing.
- **Version/platform:** Linux protocol tests do not prove native Darwin runtime or a Nix derivation. wstunnel v11.0.0 publishes darwin-arm64 assets; the catalog's Haskell `wstunnel` is not this Rust tool. Pinning/package integration, native Mac trust/SSH behavior, runtime secret ownership, and telemetry/update behavior remain gates. No telemetry-absence claim is established.
- **Revocation:** native wstunnel valid deny-all hot reload blocks new authorization but does not tear down established streams; malformed hot reload retains old policy. Immediate revocation requires a verified dedicated-server stop/change/start transaction, not watch-and-hope. Service restart must never omit restriction configuration or load stale credentials after failed update.
- **Verification still required:** deny unauthorized publishers and Mac SSH clients, prevent other relay publication/listener/normal-forward capabilities, verify fixed managed Mac destination, off removes the client and retries, nightly relay shutdown/reboot, Mac sleep/wake, stale-port cleanup, on returns promptly with relay absent, bounded noninteractive status, quiet backoff logs, no login/boot blocking, Mac key/host verification, and unchanged LAN/sing-box/unrelated app networking.
