## Exploration: Fontconfig Rules Not Being Respected

### Current State

The fontconfig system is configured in a single module: `modules/desktop/fonts.nix`. This module:
- Enables `fonts.fontconfig` with antialiasing, slight hinting, and subpixel rendering
- Sets `fonts.fontDir.enable = true` to expose fonts via X11 font directories
- Installs font packages: `source-sans`, `nerd-fonts.caskaydia-cove`, `nerd-fonts.symbols-only`, `symbola`, `joypixels`, `noto-fonts`, `noto-fonts-cjk-sans`
- Configures `defaultFonts` to prefer Source Sans 3 (sans-serif), CaskaydiaCove Nerd Font (monospace), and JoyPixels (emoji)
- Defines extensive `localConf` XML containing:
  - `<selectfont>/<rejectfont>` blocks rejecting Liberation, DejaVu, Arimo, Tinos, Cousine font families
  - Match redirect rules mapping common font names (Arial, Helvetica, Verdana, Tahoma, Geneva, Cantarell) to generic families
  - Strong aliases (`binding="strong"`) preferring Source Sans 3 > Noto Sans for sans-serif
  - Force-match rules for monospace/mono to CaskaydiaCove Nerd Font
  - Weak aliases for emoji fallbacks

**Host coverage**:
- `rog` and `thinkcentre` use the profile chain (`server.nix` → `desktop.nix`) which imports `modules/desktop/fonts.nix`. HM fontconfig not explicitly disabled.
- `t14` directly imports `modules/desktop/fonts.nix` and **explicitly disables HM fontconfig** in `hosts/t14/home/omarchy.nix` (line 123: `fonts.fontconfig.enable = lib.mkForce false`), relying on system-level fonts.nix.
- `mact2` uses nix-darwin, not NixOS fontconfig.

**Roboto**: ZERO references to "roboto" found anywhere in the codebase (no .nix files, no font config, no package lists).

### Discovery: Root Cause — localConf Is Never Loaded

After tracing the entire NixOS fontconfig module chain, I found the definitive root cause:

**The user's `fonts.fontconfig.localConf` content is written to `/etc/fonts/local.conf`, but the fontconfig `fonts.conf` generated by NixOS does NOT include it.** The local.conf file is never read by fontconfig.

#### How It Happens

1. **Fontconfig package (`pkgs.fontconfig`, version 2.18.1)** has a `postInstall` that runs an XSLT transformation on the upstream `fonts.conf`:
   ```nix
   postInstall = ''
     xsltproc --stringparam fontDirectories "${dejavu_fonts.minimal}" \
       --stringparam includes /etc/fonts/conf.d \
       --path $out/share/xml/fontconfig \
       ${./make-fonts-conf.xsl} $out/etc/fonts/fonts.conf \
       > fonts.conf.tmp
     mv fonts.conf.tmp $out/etc/fonts/fonts.conf
   '';
   ```

2. **The XSLT (`make-fonts-conf.xsl`)** explicitly DROPS all `<include>` elements from the upstream fonts.conf and only adds back the ones specified in the `$includes` parameter — which is just `/etc/fonts/conf.d`:
   ```xml
   <xsl:apply-templates select="child::node()[name() != 'dir' and name() != 'cachedir' and name() != 'include']" />
   <!-- Only conf.d is added back -->
   <xsl:for-each select="str:tokenize($includes)">
     <include ignore_missing="yes"><xsl:value-of select="." /></include>
   </xsl:for-each>
   ```

3. **The upstream fonts.conf** normally includes BOTH `conf.d` AND `local.conf`:
   ```xml
   <include ignore_missing="yes">conf.d</include>
   <include ignore_missing="yes">local.conf</include>
   ```
   But the XSLT drops BOTH and only adds back `conf.d`.

4. **The NixOS fontconfig module** creates the local.conf symlink correctly but the generated fonts.conf (which it symlinks to) doesn't include it:
   ```nix
   # This creates /etc/fonts/local.conf — but fonts.conf never reads it!
   ${lib.optionalString (cfg.localConf != "") ''
     ln -s ${localConf} $dst/../local.conf
   ''}
   ```

5. **Result**: The `localConf` — containing ALL the reject rules, redirect rules, and strong aliases — is NEVER processed by fontconfig. Only the `defaultFonts` aliases (priority 52) and fontconfig's built-in `60-latin.conf` (priority 60) are active.

This is corroborated by:
- NixOS issue #338933 ("fonts broken for some applications", Sep 2024) — which identified that a change (PR #324516) removed `<include />` directives from the generated fonts.conf, breaking font rendering
- NixOS issue #31500 ("fonts.fontconfig.localConf ignored", 2018) — a historical instance of the same problem with the `penultimate` module
- The module comment "indirect priority 51" is now misleading — local.conf has NO priority because it's never loaded

#### What IS Being Applied

Since localConf is not loaded, the following rules ARE active:
- **`defaultFonts` aliases** (priority 52): `binding="same"` aliases for sans-serif (Source Sans 3, Noto Sans), serif, monospace, and emoji
- **Fontconfig's built-in `60-latin.conf`** (priority 60): weak aliases for sans-serif (DejaVu Sans, Verdana, Arial, etc.), serif, and monospace
- **Rendering settings**: antialiasing, hinting, subpixel configuration (priority 10)

The following rules are NOT loaded (in localConf):
- Font reject rules (Liberation, DejaVu, Arimo, Tinos, Cousine)
- Font name redirect rules (Arial→sans-serif, Helvetica→sans-serif, etc.)
- Strong aliases (`binding="strong"`) for font families
- Force-match rules for monospace

#### Why `defaultFonts` Alone Is Insufficient

The `defaultFonts` generates aliases with `binding="same"` at priority 52. The fontconfig package's `60-latin.conf` provides weak aliases at priority 60. When both exist:
- Multiple aliases for the same family get **merged** by fontconfig
- With `same` binding, defaultFonts' fonts are **prepended** at the same priority level
- 60-latin.conf's fonts are **appended** at weak priority
- The final preference list for "sans-serif" is roughly: `[Source Sans 3, Noto Sans, DejaVu Sans, Verdana, Arial, ...]`
- Source Sans 3 should be tried first, but if it doesn't match for a specific weight/style, fontconfig falls through the list

The missing `binding="strong"` means fontconfig still considers the full list rather than ONLY the user's preferred fonts.

### Where Roboto Comes From

Roboto is NOT referenced anywhere in the Nix config nor in fontconfig's default `60-latin.conf` (which lists DejaVu, Verdana, Arial, Helvetica, etc. — not Roboto). Roboto can only appear from:

1. **Brave/Chromium/Google Chrome bundled fonts** (MOST LIKELY): These browsers bundle their own fontconfig library and may use their own font matching, which includes Roboto for browser UI and web content. The `browsers.nix` profile installs all three: `brave`, `chromium`, and `google-chrome`. Brave statically links fontconfig, meaning it doesn't even use the system's `/etc/fonts/`.

2. **Web content defaults**: Many websites specify `font-family: Roboto` in CSS. Even with correct system fontconfig, the browser's font matching for web content uses its OWN font stack.

3. **User-local fonts**: Possible Roboto in `~/.fonts/` or `~/.local/share/fonts/` from previous installations.

4. **Misidentification**: Noto Sans (from `noto-fonts` package, installed system-wide) shares design DNA with Roboto (both are Google-designed sans-serif fonts). The user may be seeing Noto Sans and confusing it with Roboto.

### Approaches

#### 1. Use `fonts.fontconfig.aliases` Instead of `localConf` (Recommended — lowest risk)

Replace the `localConf` block with NixOS's built-in `fonts.fontconfig.aliases` option, which goes to `53-user-aliases.conf` in conf.d (properly included).

- **Pros**: Uses native NixOS mechanism that IS properly included; declarative; survives fontconfig updates; simplest change
- **Cons**: Less expressive — only supports `alias` elements (prefer/accept/default), NOT `<match>`, `<selectfont>`, or `<rejectfont>` rules; can't reject specific fonts or redirect font names
- **Effort**: Low — modify `modules/desktop/fonts.nix` to convert localConf rules to `cfg.aliases` format
- **Files**: `modules/desktop/fonts.nix` (~50 line changes — replace localConf with aliases + add back reject rules via custom conf.d file)

#### 2. Inject a Numbered conf.d File via `fonts.fontconfig.confPackages`

Create a separate Nix package containing the fontconfig XML, add it to `fonts.fontconfig.confPackages` (internal option), which gets linked into `/etc/fonts/conf.d/` with a numbered prefix.

- **Pros**: Full fontconfig XML expressiveness; positively included via conf.d; clear priority via file numbering
- **Cons**: Requires package derivation; internal option (may change); more boilerplate
- **Effort**: Medium — create a `fc-51-nixos-custom.conf` package and add to confPackages
- **Files**: New `modules/desktop/fontconfig-custom.nix` (~30 lines) + modify `modules/desktop/fonts.nix`

#### 3. Fix the NixOS Fontconfig Module (Upstream Fix)

Contribute a fix to nixpkgs that adds `local.conf` back to the XSLT-generated includes list. This would fix the issue for ALL NixOS users.

- **Pros**: Correct fix; benefits all users; no workaround needed
- **Cons**: Requires nixpkgs PR + review + merge cycle (weeks/months); can't use fix immediately; depends on upstream acceptance; need to test across fontconfig versions
- **Effort**: Medium — modify `pkgs/development/libraries/fontconfig/make-fonts-conf.xsl` in nixpkgs
- **Files**: `make-fonts-conf.xsl` (upstream) + optionally `nixos/modules/config/fonts/fontconfig.nix`

#### 4. Use `environment.etc` to Write Directly to conf.d

Create a file at `/etc/fonts/conf.d/51-local.conf` using `environment.etc."fonts/conf.d/51-local.conf".text`.

- **Pros**: Direct and immediate; full XML expressiveness; guaranteed inclusion
- **Cons**: Bypasses NixOS fontconfig module; needs manual priority numbering; may conflict with future module changes
- **Effort**: Low — add `environment.etc` block to `modules/desktop/fonts.nix`
- **Files**: `modules/desktop/fonts.nix` (~25 line changes)

#### 5. Override `fonts.fontconfig.confPackages` with a Custom Package (Hybrid)

Combine approach 2 with approach 1 — use `aliases` for the alias rules and a confPackages entry for the reject/redirect/match rules.

- **Pros**: Separation of concerns; aliases use native module; custom rules use confPackages
- **Cons**: More complex; two mechanisms to maintain
- **Effort**: Medium — modify `modules/desktop/fonts.nix` + add custom conf package
- **Files**: `modules/desktop/fonts.nix` + new `modules/desktop/fontconfig-reject.nix`

### Recommendation

**Short-term fix (immediate)**: Use **Approach 4** — write `environment.etc."fonts/conf.d/51-local.conf"` with the full localConf content. This is the fastest path to getting the rules working again, with minimal code changes and full XML expressiveness.

**Long-term fix (sustainable)**: Use **Approach 1** — migrate to `fonts.fontconfig.aliases` for alias definitions (which it supports natively) and use Approach 4 only for the rejectfont/match rules that aliases can't express. This aligns with the NixOS module's intended design.

**Upstream**: Report/fix the XSLT issue in nixpkgs so that `localConf` works as documented. The `$includes` parameter should include both `/etc/fonts/conf.d` and `local.conf`, or the XSLT should preserve the original fonts.conf's `<include>` elements.

### Risks

- **fontconfig version sensitivity**: Fontconfig 2.18.1 behavior may differ from future versions. The upstream fontconfig project has been actively changing how fonts.conf is structured.
- **Browser font independence**: Even after fixing system fontconfig, Brave/Chromium/Chrome use their own font matching. Web content fonts are controlled by CSS, not system fontconfig.
- **GTK theme interference**: The `home-linux/theme.nix` and `hosts/t14/home/omarchy.nix` set GTK themes that may override system font preferences for GTK apps. Verify GTK settings after fix.
- **Hyprlock font name mismatch**: `hosts/t14/home/hypr/hyprlock.nix` uses "Source Sans Pro" (old name) while the system uses "Source Sans 3" (new name). These are different font families in fontconfig's eyes.
- **Roboto may not exist**: It's possible the user is seeing Noto Sans (similar design, explicitly installed) and misidentifying it as Roboto. Verify with `fc-match sans-serif` on an actual system.
