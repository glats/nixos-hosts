G305 feature work must not be advertised as shipped: [PR #369](https://github.com/AprilNEA/OpenLogi/pull/369) remains open and reports DPI write/read-back plus proposed gaming Buttons support; [PR #459](https://github.com/AprilNEA/OpenLogi/pull/459) is an unmerged onboard-profile slice with G502 X validation, not G305 release acceptance. Release tree has no onboard-profile implementation file, while `0x8090` ModeStatus has a low-level driver. [Issue #1193](https://github.com/AprilNEA/OpenLogi/issues/1193) and open [PR #1201](https://github.com/AprilNEA/OpenLogi/pull/1201) identify the missing end-to-end performance/endurance UI/agent wiring; [#1194](https://github.com/AprilNEA/OpenLogi/issues/1194) describes missing live hardware-DPI-stage events. The [official G305 guide](https://www.logitech.com/assets/65904/logitech-g305-qsg.pdf) documents G HUB onboard button/rate/mode programming and DPI stages; those hardware abilities are not equivalent to OpenLogi release coverage. The guide says performance mode is the default, contradicting #1193's endurance-default claim; read actual state rather than choosing either assumption.

Linux/macOS distinction for these devices: HID++ feature availability depends on firmware and route, not just OS. Linux standard mouse capture uses Logitech-relative-pointer evdev grabs plus uinput; the bundled rules deliberately do not grant session-wide keyboard event-node read access. K780's device-specific keyboard diversion therefore depends on supported HID++ controls rather than making all keys available through broad Linux input access. macOS uses an event tap and source attribution for mouse remapping, plus HID++ for device controls; native Agent Input Monitoring and Accessibility grants are necessary acceptance checks. Verify K780/G305 inventory and controls independently on both systems; do not treat Windows diagnostics as native acceptance.

#### Congruences and incongruences

Congruent: native Linux NixOS module and native signed macOS distribution; local per-user agent rather than cloud service; portable TOML and `Cmd` normalized to Command on macOS/Control on Linux; existing explicit host/module boundaries can select only useful hosts. MIT/Apache-2.0 code fits the repository's packaging model.

Incongruent: Linux flake versus mutable Homebrew versioning; stable nixpkgs Rust versus current-stable MSRV; GUI-owned mutable config versus HM store symlinks; macOS bundle IDs versus Linux application IDs; Wayland app_id versus X11 WM_CLASS; device recognition versus usable gaming/keyboard controls; GUI login toggles versus declaratively owned systemd service. Brand/logo assets have a separate restrictive license, so code licensing is not permission to redistribute modified branding. Headless/XRDP risks from initial exploration are contextual only because both affected Linux hosts are now excluded.

### Approaches

1. **Minimal modular platform-native integration** — one reusable local Linux module imports/enables the release-pinned upstream module, and only t14 imports the local file. macm5 uses the signed native app via existing cask ownership, with explicit acceptance of rolling cask updates or a separately chosen version-freezing mechanism. Leave live config GUI-owned.
   - Pros: reuses upstream package, udev and lifecycle; no custom daemon, shell installer, sync service, or global package migration.
   - Cons: cask names alone do not provide exact parity; permissions remain interactive; runtime compatibility still requires hardware tests.
   - Effort: Medium, primarily validation and macOS version-policy choice.

2. **Package-only trial** — after separate approval, first verify native UI and inventory without sharing config. On Linux a pure package lacks registered udev access; prefer upstream module with `launchAtLogin=false` when a real device trial is authorized, rather than adding broad input groups.
   - Pros: narrow scope, manual lifecycle, easy comparison against the prior manager.
   - Cons: installing binaries alone is not a functional remapping trial; native macOS app still needs its embedded agent and permissions. Recognition alone does not validate K780 diversion or G305 gaming controls.
   - Effort: Low to Medium; no trial performed here.

3. **Defer hardware-dependent commitments** — scope/architecture is now clear, but do not promise unverified keyboard/gaming controls or ship unreleased PR code to fill capability gaps.
   - Pros: avoids unsupported headless deployment, permission escalation and invented defaults.
   - Cons: does not provide replacement controls yet.
   - Effort: Low.

### Recommendation

Verdict: **architecture is feasible and sufficiently scoped for a future narrow proposal, but proposal/adoption execution is not authorized**. Option 1 is the smallest durable architecture: one local Linux module plus one t14 import, existing native macOS cask ownership, local mutable config, and hardware acceptance gates. Existing `specialArgs.inputs` makes builder edits unnecessary. rog and thinkcentre remain unchanged/disabled. OpenLogi is a GUI application plus input-capable per-user agent, not an MCP, skill, operational helper, or network sharing service.

G305 has a meaningful potential DPI/battery benefit even without comprehensive gaming controls; K780 discovery/battery is evidenced, but remapping/Fn-lock claims must be conditional on actual feature/control probes. The unidentified LIGHTSPEED mouse does not prevent defining this architecture. Flow, synchronization and automatic switching are explicitly excluded rather than questions to ask again.

#### Config ownership and identity

Use release documentation/examples, not the site's schema-4 marketing demo. [CONFIGURATION.md](https://github.com/AprilNEA/OpenLogi/blob/v0.8.11/docs/CONFIGURATION.md) requires schema 7, rejects unknown/newer fields, and describes atomic writes with five backups and external-edit refusal. [config.example.toml](https://github.com/AprilNEA/OpenLogi/blob/v0.8.11/docs/config.example.toml) additionally documents schema-5+ `unit:<hex>`/`serial:<s>` canonical identity, historical receiver-route migration, measured per-link capabilities and overrides. This detail is not fully reflected in the prose's receiver examples. Capture actual generated keys on each host and transport; do not invent device/model keys or assume every device exposes a unique serial/unit ID.

A Home Manager store symlink is the wrong default for this live file: atomic replacement may fail or replace the symlink, and later activation can restore declarative state over GUI changes. Keep it GUI-owned and host-local; no HM module, seed or synchronization is needed for clarified platform coverage. App selectors, app launch paths, compositor shortcuts, identity/link metadata and permission/startup preferences remain local. Keep GUI and agent from the same release/protocol generation; avoid downgrading binaries over a migrated newer schema without its matching backup.

### Risks

- [Linux installation docs](https://github.com/AprilNEA/OpenLogi/blob/v0.8.11/docs/INSTALL-linux.md) and [udev rules](https://github.com/AprilNEA/OpenLogi/blob/v0.8.11/packaging/linux/udev/70-openlogi.rules) grant active-seat uaccess for Logitech hidraw, mouse-only event nodes and uinput. This enables input capture/injection; it is not privilege-free. No broad input group should be added. Headless/remote seats and multiple sessions remain unproven.
- Upstream module ties WantedBy/PartOf to graphical-session.target and restarts on failure; GUI-created high-priority user units/login toggles could conflict with Nix ownership. Use NixOS as t14 lifecycle owner and the signed app's embedded Login Item on macm5. Do not add global services or modify excluded remote hosts.
- Quit competing Logitech managers before native trials: Options/Options+, G HUB for gaming controls, Solaar and other active HID++ managers may contend for the same device or overwrite state. Upstream expressly warns about Options+/Solaar; G HUB is documented as the G305 configuration owner, so concurrent-operation safety must not be presumed. Detect installed/running managers without uninstalling or restarting anything during exploration.
- [IPC transport](https://github.com/AprilNEA/OpenLogi/blob/v0.8.11/crates/openlogi-ipc/src/transport.rs) uses a local Unix socket normally at `~/.config/openlogi/agent.sock`, not a TCP sharing listener. It creates the parent and listener but this inspected layer does not establish restrictive modes or peer credentials. Actual umask, parent/socket permissions, upstream agent authentication and all optional features' listener surfaces remain security unknowns; no firewall ports should be added.
- [Website](https://openlogi.org/) claims no account/telemetry; it expressly discloses device renders from public CDNs and opt-in update checks off by default. Release example sets asset auto-download true and update checking/installation false. Therefore “never phones home” is not a zero-network guarantee. CDN probing, mirrors, update endpoints and corporate-network policy require review; settings are claimed local, not independently traffic-audited.
- Public GitHub security-advisory API returned an empty list on the research date, not a clean security bill. Release Cargo.toml raises tarpc to >=0.38 to avoid transitive advisory GHSA-w9wp-h8wv-79jx. No full dependency/security audit performed. Broad issue searches include ordinary macOS permission reports, not necessarily vulnerabilities.
- Upstream issues provide relevant prior art: [#705](https://github.com/AprilNEA/OpenLogi/issues/705) is a closed older NixOS GUI crash; [#1290](https://github.com/AprilNEA/OpenLogi/issues/1290) is an open Wayland remapping report; [#1135](https://github.com/AprilNEA/OpenLogi/issues/1135) and [#1304](https://github.com/AprilNEA/OpenLogi/issues/1304) are open macOS agent permission reports. These warrant acceptance tests but do not establish v0.8.11 failure on this hardware.
- Source availability limits: Context7 and Exa returned useful but partly stale docs; website schema/profile claims and Linux installation docs disagree with release source. Release source now proves a native Wayland foreground backend, correcting the earlier XWayland-only interpretation. Exa privacy-page fetch returned `CRAWL_NOT_FOUND`. Initial NixOS MCP options-browse action was unsupported; corrected options search verified the surface. Stable MCP search is not exact pinned-package evaluation. K780 GitHub code-name search returned zero hits, but device diagnostics provide positive inventory evidence. Unreleased PRs and Windows diagnostics are not native Linux/macOS acceptance. Runtime managers, permissions/socket isolation, chosen transports, desired control expectations and the additional LIGHTSPEED mouse's identity remain unknown. The excluded Flow/sync goals are no longer unresolved requirements.
