# Spec: hyprsunset-config

> Domain: hyprsunset blue-light filter configuration via Home Manager module.
> Host: t14 (nixos-hosts) + omarchy-nix upstream (module source).
> Source files: `hosts/t14/home/hypr/hyprsunset.nix`, omarchy-nix `modules/home-manager/hyprsunset.nix`.

---

## REQ-HS-001: Migrate hyprsunset from xdg.configFile to services.hyprsunset

**What**: The hyprsunset configuration SHALL use the declarative `services.hyprsunset.settings` Home Manager option instead of raw `xdg.configFile."hypr/hyprsunset.conf"`.

**Why**: Home Manager provides `services.hyprsunset` module with declarative `settings` option that generates the config file and systemd user service. Using the HM module eliminates the raw config blob, provides option validation, and deduplicates the systemd unit definition.

**Architecture**: Two layers exist:
- omarchy-nix upstream: `modules/home-manager/hyprsunset.nix` sets `services.hyprsunset = { enable = lib.mkDefault true; settings.profile = lib.mkDefault [ { time = "07:00"; identity = true; } ]; }`
- t14 host: `hosts/t14/home/hypr/hyprsunset.nix` overrides `settings.profile` with `lib.mkForce` for a progressive 5-profile schedule

**Current schedule** (t14):
- 07:00: identity (no filter)
- 18:00: 4500K
- 19:30: 4000K
- 21:00: 3500K
- 23:00: 3000K

#### Scenario: Declarative config generates valid hyprsunset.conf

- **Given** `services.hyprsunset.settings` is configured with 5 profiles
- **When** Home Manager activation writes the hyprsunset config file
- **Then** the generated `~/.config/hypr/hyprsunset.conf` SHALL contain valid format
- **And** the progressive warming schedule SHALL match the 5-profile list

#### Scenario: systemd user service is generated by HM module

- **Given** `services.hyprsunset` is enabled via the HM module
- **When** Home Manager activation generates systemd user units
- **Then** `systemd/user/hyprsunset.service` SHALL exist
- **And** it SHALL NOT conflict with any manually-defined unit

#### Scenario: No duplicate systemd unit conflict

- **Given** the omarchy-nix upstream HM module no longer defines `systemd.user.services.hyprsunset` manually
- **When** `nix flake check --no-build` is run for t14
- **Then** no "option defined multiple times" warning SHALL appear for `systemd.user.services.hyprsunset`

#### Scenario: t14 host-specific profiles are preserved

- **Given** the t14 user wants progressive warming
- **When** `services.hyprsunset.settings.profile` is configured with 5 entries
- **Then** the profile list SHALL be the t14-specific schedule
- **And** the omarchy-nix default profile SHALL be overridden

#### Scenario: omarchy-nix upstream PR is required first

- **Given** the t14 config depends on omarchy-nix's migrated hyprsunset module
- **When** the nixos-hosts flake input is not yet updated
- **Then** a build conflict SHALL occur (two sources defining the same config file)
- **Therefore** the omarchy-nix PR SHALL be merged and the flake input updated BEFORE applying t14's hyprsunset changes

## REQ-HS-003: Validate hyprsunset profile format at build time

**What**: When declarative `services.hyprsunset.settings` is used, the Home Manager module SHALL validate that profile entries have valid `time` and `temperature` or `identity` fields.

#### Scenario: Valid profiles pass validation

- **Given** all profile entries have valid `time` (HH:MM, 00:00-23:59) and valid `temperature` (1000-10000) or `identity = true`
- **When** `nix flake check --no-build` is run
- **Then** the validation SHALL pass
- **And** the config file SHALL be generated successfully
